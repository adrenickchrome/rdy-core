# Signed preview release workflow

This repository keeps the founder's offline FIDO/Ed25519 SSHSIG release key.
GitHub builds and checks candidates; it never receives that private key or a
signing-agent socket. Current distribution targets are Linux x86-64 GNU and
macOS ARM. Windows source checks are not a Windows distribution promise.

The workflows are implemented source. They become operational only after real
hosted qualification and the repository controls below are installed and read
back. The existing v0.17.0 preview must not be overwritten to test this pipeline.

## One-time activation

1. Merge the reviewed pipeline through the factory's source process. Observe
   actual `Core CI`, `Core platforms` and `Core security` aggregates on main.
   They must pass at the exact release source. Advisory coverage failure is not
   hidden; performance and milestone deep QA remain external factory authority.
2. Review main/tag protections and the exact Nick exception. A personal public
   repository does not have organization Enterprise required-workflow isolation.
   Protect workflow/control changes through code-owner review. Ordinary jobs
   have no secrets or write credentials; never use persistent factory runners
   for untrusted PR jobs.
3. Enable immutable releases for future publication and preserve native settings
   readback. Create `core-preview-release`, restrict deployment to main, require
   Nick's approval, allow his self-review while he is the only human reviewer,
   and disable administrator deployment-rule bypass. In that environment set
   `CORE_RELEASE_CONTROLS_READY=true` only after those controls are verified.
   No release secret is needed. Environment creation by workflow reference alone
   is insufficient and leaves this activation variable unset.
4. `GITHUB_TOKEN` has no Administration:read permission. The immutable-release
   settings endpoint requires that permission, so the publisher cannot pre-read
   it. The approving owner must confirm the native setting remains enabled.
   The workflow checks actual `immutable: true` after publication and refuses
   destructive repair. This is a visible limit, not an independent prepublication
   admin-settings guarantee. Do not add an administrator secret to work around it.

Standard public hosted runner compute requires no new paid runner purchase.
Artifacts expire after seven days; artifact storage remains subject to GitHub
billing/quota. No larger runner or storage-limit increase is part of this setup.

## Prepare a candidate

Prepare a new plain `0.N.0` version through the core factory. Its exact main commit
must already have all three successful main-push workflow aggregates. The
candidate source and release control revision must be identical. Do not advance
main between candidate generation and finalization; if it advances, dispatch a
new candidate and sign the newly generated bytes. Never rebuild under an old
signature. Candidate workflow reruns are refused; use a new explicit dispatch.

Prepare a sanitized external factory qualification object with this structure.
Use the actual source, commands, evidence digests, stable credential-free HTTPS
receipt locations and machine classes. Performance must name an existing class
in `crates/rdy-qa/qa-baseline.json`. No raw private log or host path belongs here.

```json
{
  "schema": 1,
  "source_sha": "EXACT_40_HEX_MAIN_COMMIT",
  "agent_guide_sha256": "REVIEWED_SCRIPTS_RELEASE_AGENT_GUIDE_SHA256",
  "deep": {
    "result": "pass",
    "command": "ACTUAL_DEEP_COMMAND",
    "evidence_sha256": "ACTUAL_64_HEX_RECEIPT_HASH",
    "evidence_uri": "https://YOUR_APPROVED_EVIDENCE_LOCATION/deep-receipt.json",
    "machine_class": "ACTUAL_MACHINE_CLASS"
  },
  "performance": {
    "result": "pass",
    "command": "ACTUAL_PERFORMANCE_COMMAND",
    "evidence_sha256": "ACTUAL_64_HEX_RECEIPT_HASH",
    "evidence_uri": "https://YOUR_APPROVED_EVIDENCE_LOCATION/performance-receipt.json",
    "machine_class": "EXACT_EXISTING_BASELINE_MACHINE_CLASS"
  }
}
```

The end-user guide source is `scripts/release/agent-guide.md`, imported verbatim
from the public v0.17.0 AGENTS.md asset (asset 664223297, 20,715 bytes,
SHA-256 `c0eece7829d7c9792516589273bffe802dd00c6f866aba9fdd1d6c1266bba913`).
The matching public CLAUDE.md asset 664223312 has the same digest. Both future
release names come from this one tracked end-user source, never the repository's
developer AGENTS.md. The factory must review its compatibility with the next
preview and bind its current digest in the qualification receipt; update the
tracked guide through normal source review when product commands change.

This is attributed factory evidence, not proof that hosted QA reran a benchmark.
The source binding and missing/nonpass fields are enforced; the release owner
must inspect the underlying receipts. Do not fabricate a passing receipt to
unlock the candidate. A private authorized evidence service may supply the stable
URI, but credentials never appear in it or in workflow inputs.

Dispatch **Core release candidate** on main with the new plain version and the
one-line base64 encoding of that JSON. It performs admission, fresh native fast
QA, clean package builds, architecture/ABI/path inspection, resolved-Cargo-graph
CycloneDX SBOMs, fixed archive checksums and GitHub provenance. Build requirements
are observed, not assumed supported minimum OS versions. The SBOM includes build
dependencies; it is not a claim that every component is linked at runtime.

Download the successful run's `candidate` and `provenance` artifacts. Review
`candidate.json`, `admission.json`, both build records, required-check runs and
factory receipts. The signing packet names the source/control revision, run and
attempt, native artifact IDs/digests, per-file digests and the canonical manifest
SHA. The signature covers exactly the two archives, using the existing product
contract. Installer, guide, SBOM and receipt hashes are separately bound to the
source/candidate and GitHub provenance; they are not secretly added to that
SSHSIG manifest.

## Offline signature and finalization

On the founder's signing machine, verify the packet and sign **the exact**
`SHA256SUMS` using the existing dedicated release key:

```sh
ssh-keygen -Y sign -f /path/to/existing/release-key -n rdy-release-v1 SHA256SUMS
```

That private path is entered locally. Do not upload the private key, copy it to
CI or supply a signing socket. The output `SHA256SUMS.sig` is public signature
data. Encode that file as one line (portable Python example):

```sh
python3 -c 'import base64,pathlib; print(base64.b64encode(pathlib.Path("SHA256SUMS.sig").read_bytes()).decode())'
```

Dispatch **Core signed preview publication** on the same main revision with:

- The successful first-attempt candidate run ID.
- The exact SHA-256 of `SHA256SUMS` shown in the signing packet.
- The one-line base64 of the public signature, at most 5,500 characters.

The read-only verification job resolves only the candidate/provenance artifact
IDs in that run. It validates source/control/repository/version/expiry/file sets,
checks GitHub attestation source and signer identities, and verifies the founder
SSHSIG against the pinned public key. Native read-only jobs then execute the
existing install checker (CLI, isolated project, daemon and MCP) and new managed
installer on both platforms. No existing developer installation or project is
used as a fixture.

Only after native acceptance does the protected publish job request approval.
Review the exact source, version, evidence and immutability setting. The job has
contents-write access only for draft assembly/publication, plus Actions read
access for candidate identity checks. It executes trusted control helpers, never
candidate binaries or candidate build scripts. The two exact native reports produce a durable, sanitized
`release-qualification.json` (source, targets, result and receipt digests, without
scratch paths). All assets are attached to a draft, verified by remote size and digest, and published once as a prerelease.

Fresh public-download install acceptance runs explicitly in the same workflow on
Linux and macOS. It does not rely on `release.published` recursion: releases made
with `GITHUB_TOKEN` do not trigger ordinary follow-on workflows. A publication
success followed by postflight failure is a release incident, not overall success.
The initial signed installer remains preview-only and never uses `/releases/latest`.

## Failure, retry and retention

- Changed, expired, ambiguous or missing candidates refuse continuation. Generate
  a new run and signature when bytes or source change; do not extend old evidence.
- An uncertain GitHub write stops. Read the actual release/tag/asset identities
  before explicitly dispatching a continuation. A matching partial draft uploads
  only missing assets; mismatched/foreign assets or tags refuse without deletion.
- Every continuation performs fresh native acceptance. If the draft or published
  release already contains `release-qualification.json`, its original bytes are
  retained. The publisher checks the original exact-source finalization run,
  both successful native jobs, and both retained acceptance artifact hashes and
  receipt bodies before reuse. Different new run IDs or temporary paths do not
  overwrite historical evidence. A failed publication run is acceptable evidence
  only when its native acceptance jobs succeeded; missing, expired, changed or
  rerun original evidence refuses continuation. The seven-day artifact window
  still applies. Later public-install failures remain incidents to investigate.
- An already published exact immutable release is reconciled without mutation.
  A published defect needs a fresh version, not asset replacement or tag movement.
- Repository control activation and immutable release publication are distinct
  from source preparation. Local fixture tests do not establish native hosted
  acceptance, a real founder signature for a new version, or public distribution.
- Preserve the first failure and actual skipped-test counts. `--require-all` does
  not execute ignored tests, and `--skip-perf` is not the full factory gate.
- The installer manages binaries only. It does not migrate projects or restart
  daemons. Retain the old binary for the preview old-dump → new-empty-load flow.

For local control checks (Python 3.11 or newer):

```sh
python3 -m unittest discover -s tests/release -v
bash -n scripts/release/build.sh
```
